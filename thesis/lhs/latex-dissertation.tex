\section{Introduction}


\subsection{Game-theoretic modelling as a software problem}

Tackling a complex problem by decomposing it into bite-sized pieces is perhaps the name-of-the-game in software engineering. A software engineer needs to design the correct abstractions for composing, removing, and extending blocks of code that can be conceived in isolation but ultimately brought together for a complete solution to a problem. On top of that, maintaining a code-base can often be a collaborative effort, with ever-changing requirements and unforseen bugs that stretches across different modules. Some solutions to maintaining the efficiency and stability of the code-base typically involve continuous integration, design patterns (i.e. Gang of Four), or perhaps just some human-readable variable names. 

Let's try to generalize the software engineering process as follows: a software engineer observes the problem, hypothesizes a solution and lists assumptions, they prototype an implementation as some program, tests the solution, observes the output of the program to verify assumptions, and adjusts the implementation accordingly, not unlike the process shown in Figure~\ref{figure:Fig. 1}. 

Similarly, the transition from real-world phenomena to a game-theoretic model requires observing the real-world, developing abstractions according to standard game-theoretic concepts, and observe the behaviour of the game under certain conditions. Evaluation metrics include observing the respective payoffs of players under certain conditions, or determining whether a strategy profile is a Nash equilibrium. The task is left to collate these metrics and derive expectations of the players' as rational and utility-maximizing. Indeed \textit{mechanism design} is specifically concerned with sculpting these games to achieve a hypothesized outcome under certain conditions. 

The process of instantiating these games are (expectedly) domain-specific. Building a model too general fails to become useful, and a model too specific. Drawing from \cite{Zahn2024}, compositional game theory has enabled a strong correspondence between game-theoretic models and code. With the proper abstractions for piecing models together, developing a library of economic models that can be easily loaded and run as for simulations is within grasp. Focusing in again on "models as code", we can naturally correspond software engineering principles to game-theoretic modelling principles. The practical implications of compositional game theory were first explored in \cite[section 2.3.12]{HedgesThesis}, developing the first steps to compositionally designing problems. Constructing games for these problems using string diagrams ultimately transitioned to an implementation of the category of games as a Haskell library. Hence, we have a mechanical process that can be used to assist a modeler to understand a problem in terms of compositional game theory. However, there has yet to be a more explicit methodology for effectively using the tool, specifically outside microeconomic analysis. Rather than taking a domain-constrained approach to the tool, this thesis seeks to identify techniques using this DSL as part of a larger software-development process in order to build effective models.

\subsection{Why cybersecurity games?}

The development of cybersecurity models are increasingly more important in today's landscape of technological interconnectivity. It's a modeller's responsibility is to accurately reflect dynamic attack and defensive scenarios, from DDoS (Distributed Denial of Service) attacks on smart grid networks, to intrusion detection and response systems in distributed computer networks. Game-theoretic models have been widely accepted as a tool for enhancing the defensive capabilities of a system. By modelling the interaction between an attacker and defender, where the players are rational actors maximizing their utility, a modeller can derive an optimal defensive strategy or predict an attacker strategy. Using these findings, a security administrator can deploy countermeasures preemptively, or evaluate real-time adjustments to a defensive strategy. 

There has been growing interest in developing these game-theoretic models in a variety of security domains, requiring collaborative expertise between game modelling and cybersecurity. Based on the inherent relationships between these models, we propose a methodology to expressively derive these security games from smaller games using compositional game theory. But why study these relationships in the first place? The answer is to towards developing an answer to an auxiliary question: how do we develop the "correct" models? Or more tractably, which models actually improve the performance of security systems? Evaluating a security system means considering system performance, internal impact between subsystems, and different adversary capabilities. Though the game formulation process is grounded by the same game-theoretic concepts across these models, 

So beyond developing a system to just construct security games from smaller ones, the game formulation process should be a \textbf{experiential} and \textbf{collaborative} effort. By modularizing this game formulation process, we can create greater interoperability and rapid model adjustment. Essentially by inverting the process by starting at simple components, we allow for generalization to a security situation through parameterization to \textit{grow} the model, rather than \textit{restrict} a security scenario to fit the confines of the game.

\subsection{On using Haskell} 
This thesis fully embraces the Haskell for designing these cybersecurity games. By the end, we hope the reader will have benefited from an explicit account of using the open game engine in its current form. However, the software abstractions needed to engage in this workflow effectively can obfuscate the purpose of the study, namely to bridge the design and simulation of these game-theoretic models in a declarative way. While this thesis strongly persists in using software methodologies to facilitate this design process, ultimately the DSL portion and Haskell portion of this work coalesce. Nonetheless, as this study progressed, we found that Haskell language features such as using monads or property-based testing were effective for simulation, test data generation, and model parameterization. 

On the other hand, a user should  be able to use the DSL as a sufficient environment for the purposes of visualizing information flow and structuring players while hiding the implementation details needed to instantiate the game. This ends up being a significant learning curve by requiring a user to translate simple real-valued reward functions to a Haskell function, or adding model parameters as part of an abstract data type. But the hope is that by adopting this layer as an intermediate language and taking the time to encode these calculations as Haskell functions, this will enable quick-and-easy compatibility of models. Thus a particular area that this thesis addresses is formalizing a "how-to" for games beyond the syntax for using the open-games DSL.

\subsection{Introduction}
The primary focus of this thesis is on developing a methodology for the game formulation of cybersecurity models using a Haskell domain-specific-language (DSL) for \textit{open games}. 
The organization of this chapter is based on the construction of the model of computation
for open games. These constructions will then be accompanied by their corresponding implementation,
available as typeclasses or type constructors as part of \ensuremath{\Conid{\Conid{OpenGame}.\Conid{Engine}.Engine}}. The remaining chapters of the thesis 
will propose design patterns and techniques for rapidly developing security models using the tool presented here.

Compositionality in game theory enables a wider range possibilities for modelling, in particular how to develop a particular way to refine this model modularly. Even based on the intuition of deciding the rationality of agents, we can confer their behaviour based on their percieved context, whether that's actions of other agents they directly observe, or the result of some sort of computation. 
Furthermore, abstracting away the specific behaviour of agents by describing a well-defined type system, allowing a software engineering approach, can enable a contextual understanding of an agent as part of a larger system. 
That dependence and ability to decouple the problem is enabled by considering utility-maximizing agents as a kind of open system, reacting to its environment. 
In the case of compositional game theory, we can start by using the concept of an open game. The properties of an open game allow a particular modelling workflow to assist a 
user in testing modelling assumptions or design choices programmatically. If the end goal is for users to treat open games as first-class citizens of this workflow, we want to delve into the underlying theory before 
describing these design patterns. 

To get started with the tool, users will need \href{https://www.haskell.org/ghcup/install/}{\textbf{ghc}}, 
and a package manager such as \href{https://docs.haskellstack.org/en/stable/}{Stack}. 
From here on we will refer to the \textit{open-game-hs} as the library that can be included 
as a dependency in a Haskell project. The main module is \ensuremath{\Conid{\Conid{OpenGames}.\Conid{Engine}.Engine}}, where all 
the library's functionalities are available. On the other hand, we'll refer to the code block 
syntax (the DSL) that is compiled to a program that could be expressed with just the library functions. The purpose of the DSL is to give a language to construct open games with explicit input and output ports, and implicitly facilitate parallel and sequential composition by "plugging" these ports together. 

But black boxing into this DSL the development of these models may not be enough to create intuitive models. If we wanted to ship a certain model expressly as a series of open games written in the DSL, the only constraints to guide its usage comes down to specific functions exported by \ensuremath{\Conid{\Conid{OpenGames}.\Conid{Engine}.Engine}} to construct well-typed games and run diagnostic functions. The process of generating strategies to run the game, reading through the console output of simulating the game, or refactoring a single input variable within the game, requires deeper knowledge of \ensuremath{\Conid{\Conid{OpenGames}.\Conid{Engine}.Engine}}. 

We can start by examining the following code example which acts as a typical template game for defining larger security games.

\subsection{Classical game theory}


Game theory is a mathematical formulation for modelling strategic interactions between self-interested actors. To encapsulate this self-interest in quantifiable game theoretic models, we can define a certain reward (or payoffs) according to a set of actions for each player. Typically, this is written as a real-valued payoff function that measures the "happiness" of an agent for each possible action. Thus, we can evaluate the reward for each agent when they act or react according to a \textit{strategy profile}. We refer to classical game theory in the sense of the original instantiation of game theory as it was used in mostly economics. Readers can use \cite{leyton2008essentials} as reference for the few classical game theory terms used in this thesis.
Since we primarily rely on constructing games using compositional game theory, we found that classical game theoretic terms come more in handy as a post-hoc interpretation and evaulation of these models. Another way to put this is compositional game theory boils down to classical results, but it is more useful not to restrict ourselves by thinking classically from the get-go. This is especially relevant when constructing games in the domain of application, in this case cybersecurity games.

\subsection{Concrete lenses and open games}
Open games that are used in this thesis first relies on machinery that enables the flow of "forwards" and "backwards" 
information flow. This is encoded using the language of 
\textit{lenses}. Historically, open games were constructed without any connection to 
lenses, but was most recently used for defining Bayesian games in \cite{BayesianOpenGames} using a more general 
definition which broadly encompasses
the more familiar term, \textit{lenses}. 

Lenses have been used in database theory, defining certain 
\textit{lens laws} associated with data accessors. These properties dictate the behaviour 
of a \textit{get} and \textit{put} operations (or colloquially, \textit{view} and \textit{update} operations).
High-level, \textit{get} allows you to view the contents of a substructure, and 
\textit{put} allows you to make updates to a substructure, and the lawfullness of these operations ensure that 
updates to the substrucuture are reflected accordingly in the larger structure. Thus a lens (given by $lens: S \rightarrowtail A$) is a pair of operations typed as $get: S \rightarrow A$
and $put: S \times A \rightarrow S$, where $A$ is the substructure of $S$. But we can relax the requirement of "substructure"
and generalize \textit{get} and \textit{put} to the definition of concrete lenses:

\begin{definition}(Concrete lenses from \cite[Definition 2.2.1]{BayesianOpenGames}) Let $S$, $T$, $A$, $B$ be objects of 
the category $\Set$. A \textit{concrete lens} l: $(S,T) \rightarrowtail (A,B)$ is a pair of functions 
$u: S \rightarrow A$ and $v: S \times T \rightarrow B$
\end{definition}


To see what this would look like in Haskell, we can treat $u$ and $v$ as the two parameters for instantiating 
a datatype

One of the important features of these lenses is that they compose sequentially and in parallel,
or in other words, act as morphisms of a symmetric monoidal category where objects are pairs of sets. 
We term sequential composition as morphism composition and parallel composition as the tensor product of the 
symmetric monoidal category. Note that 
$S$ and $A$ are the types for domain and codomain of the
covariant morphisms and $R$ and $B$ are the domain and codomain for contravariant morphisms of these lenses.

To hint at where we are headed towards describing open games as \textit{processes that care about their environment}, intuitively
such a morphism would describe the behaviour of an agent given a certain strategy when operating 
in a given environment, where: 
\begin{itemize} \label{note:hint}
   \item Makes observations of type $S$
   \item Takes actions of type $A$
   \item Recieves some feedback from its local environment of type $T$
   \item Relays information back to the environment of type $B$
\end{itemize}
Thus given (1) a strategy $S \rightarrow A$, (2) an observation of type $S$, and (3) some continuation or feedback 
providing some payoff of type $B$, we will be able to describe what this strategic agent would do to maximize its expected payoff.

Considering the behaviour of agents using these lenses is enough to start constructing a category 
of open games that can model normal-form games \footnote{(see \cite{HedgesThesis,hedges2017morphismsopengames,BayesianOpenGames} to see how 
this is done and the construction of the category of open games)}. We'll only mention that this category of \textit{concrete open games}
exists, and choose to focus on the successor which is not limited to a deterministic setting. 
For security games or modelling realistic security scenarios, most current models use
mixed strategies, Bayesian games, or incomplete information games.

\subsection{Coend lenses and probability}
To accommodate the need for modelling games in a probabilistic setting, we would need a more generalized notion of lenses (and then a more general category of open games), where we can do things like take actions $A$ 
over some probability distribution, or give agents the ability to have some probabilistic belief about their type (as in classic Bayesian games). This turns out not to be as simple as attaching a probability monad 
to the current definition of lenses, specifically because the tensor product of the category of open games fails to be associative. 
\footcite[Section 3.4]{BayesianOpenGames}
Instead, the authors of 
\cite{3} use \textit{coend lenses} (or \textit{optics}). 

We recall the definition from \cite[Definition 2.0.1]{riley2018categories}

\begin{definition}[Coend lens] \label{Definition:Coends}
   Given a symmetric monoidal category $\C$ equipped with tensor product $\otimes$, and with pairs of
   objects $(S,T)$ and $(A,B)$, a \textit{coend lens} 
   $l: (S, T) \rightarrowtail (A, B)$ is an element of the set $\int^{\Theta:\C} \C(S, \Theta \otimes A) \times \C(\Theta \otimes R, T)$
\end{definition}

Treating $\C$ as $\mathbf{Set}$ produces the definition of the concrete lenses introduced in the previous section. 
Explicitly, we can treat this set as the pairs of functions $u: S \rightarrow \Theta \otimes A$ and $v: \Theta \otimes B \rightarrow T$
quotiented by the equivalence relations given by $((f \otimes A)u, v) ~ (u, v(f \otimes B))$ for any 
$f: \Theta \rightarrow \Gamma$, $u: S \rightarrow \Theta \otimes A$ and $v: \Gamma \otimes B \rightarrow T$. 

Effectful lenses have been studied in \cite{xie2025effectful,abou2016reflections}, but \cite[Section 4.9]{riley2018categories} implements some desired effectul properties as "effectful 
optics" using the coends as defined here with the appropriate monad (i.e. Writer, State). Since the specific application we 
are interested in for game theoretic modelling is the ability to describe, for example, \textit{behavioural strategies}
and moves of Nature, we use the finite distribution probability monad. 

Based on the intuition we've introduced in the previous section, a \textit{behavioural strategy} would 
then have to be represented by a function of type $S \rightarrow \Prob(A)$ where $\Prob(A)$ is the finitary probability distribution
monad over the actions $A$. This monad is an important type constructor 
used in the \textit{open-game-engine} for wrapping user-defined types, specifically 
the constructor \ensuremath{\mathbf{type}\;\Conid{Stochastic}\mathbin{::}\Conid{T}\;\Conid{Double}}, where \ensuremath{\Conid{T}} is the probability monad 
given by the module \ensuremath{\Conid{\Conid{Numeric}.\Conid{Probability}.Distribution}}.

\subsection{Open games}
Now that we've set our formalization for stochastic optics, we can introduce the  interpretation for these morphisms of $\mathbf{Optic}_{\KlD}$, which describes an \textit{open play} according to a supplied strategy. This open play along with a best-response relation over the possible strategies will be the components of an open game. We'll start with the formal definition of general open games from \cite[Definition 3.6.1]{BayesianOpenGames} and then demonstrate each of its components. 

\begin{definition}[Open game]
   An open game is comprised of the following data, with $(S,T)$ and $(A,B)$ objects of $\StochOpt((S,T), (A,B))$: 
   \begin{enumerate}
      \item A set of strategies $\Sigma$
      \item A \textit{play function} $P: \Sigma \rightarrow \StochOpt((S,T), (A,B))$
      \item A \textit{best-response function} $B: \Sigma \rightarrow \mathbb{C}((S,T), (A,B)) \rightarrow \mathcal{P}(\Sigma)$
   \end{enumerate}
\end{definition}

Given a strategy from the set of strategies from (1) that assigns an outcome of type \ensuremath{\Conid{Stochastic}\;\Varid{a}} representing probability distribution over actions for each observation of type \ensuremath{\Varid{s}}, we generate a stochastic optic that is "preloaded" with the behaviour of this strategy. This optic \ensuremath{\Conid{StochasticOptic}\;\Varid{s}\;\Varid{t}\;\Varid{a}\;\Varid{b}} is open in the sense that it's ready to respond by choosing an action according to its local \textit{context} \footnote{see the following section, \ref{sec:contexts}}. So we can describe a family of optics indexed by behavioural strategies using the Haskell function:

So far we alluded to the idea of \textit{context} in open games. Contexts have taken many different forms in the literature, from more bare-bones necessitation of a \textit{history/cohistory} and \textit{continuation} pair, to more formally using a \textit{context functor} to define contexts as elements of $\mathbb{C}((S,T),(A,B))$.

The name of the (open) game is to describe rational agents interacting with some environment. Thinking about Nash equilibrium in classical game theory, in equilibrium players are not incentivized to change their action assuming they know the other players' strategy. In the field of view of players, we act according to how we expect other players to act. Starting to think of each of these open games as programs, an open game has four types associated with it. 
Here variables $X, Y$ are flowing covariantly (intuitively, flowing forwards) and $S, R$ are flowing contravariantly (which represent the feedback of information). Specifically: 
\begin{itemize}
	\item $X$ is the set of inputs that the open game can observe 
	\item $Y$ is the set of actions that the open game can take, or \textit{outcomes}
	\item $S$ is the set of \textit{co-outcomes} with the purpose of propagating information to precomposed games. 
	\item $R$ is the set of \textit{outcomes}
\end{itemize}

The syntax is divided into two sections, (1) the external components and (2) the internals of the open game. The external components are comprised of the two fields \ensuremath{\Varid{inputs}} and \ensuremath{\Varid{feedback}} above the delimiter \ensuremath{\mathbin{:----:}}, and \ensuremath{\Varid{outputs}} and \ensuremath{\Varid{returns}} at the bottom. Note that user-declared variables are in scope for the internals of the game and correspond with the \ensuremath{\Varid{inputs}} and \ensuremath{\Varid{returns}} fields. On the other hand, the remaining two fields designate the values that will be generated by the internals of the game to be passed to other games. As in the above example, the variables declared in the outputs field can be used in any of the inputs or returns fields.


We treat any parameters such as \ensuremath{\Varid{exoVar}} as exogenous parameters introduced outside the game. This ends up being an appropriate place to pipeline the infrastructure required to characterize payoff functions, parameterize strategies, and other techniques in order to keep the DSL syntax generic. See Chapter \ref{sec:designPatterns} for the infrastructure and coding patterns used to best utilize this concept.

By exposing the first player's decision to the second, the model execution code should fail to compile because now the strategy of player 2 is dependent on this variable. \section{Modularity in game theoretic cybersecurity modelling}
\label{sec:designPatterns}
\subsection{Overview}

The stark reality of designing effective cybersecurity games is bridging real-world security concerns with an accurate representation in a game-theoretic terms. Numerous models have been constructed and analyzed according to specific security problems, thus tying the models to their specification. Furthermore, these models often extend or adapt previously existing constructions by making new assumptions, using different payoff schemes, or integrating the model into an automated defensive infrastructure. Although this informal relationship between these models have been surveyed, there has yet to be a generalized framework for mechanizing this relationship as a standardized game formulation process. On the other hand, as a software tool, open games can accommodate the security models setting, but not without specific Haskell setup-code for running and evaluating a model. Insofar that for investigating a large problem, an open games user can end up with a huge series of top-down Haskell scripts representing a specific simulation, with few structural or helper modules to tie everything together. In order to effectively develop a game formulation process using this tool, we need to identify compositional trends in cybersecurity games, then implement a small Haskell library to provide templates and helper functions for leveraging these compositional trends. Finally, we can follow a cybersecurity-games-as-code approach to iteratively test, generate, and improve models.
This culminates to a metamodelling design process over the open-games-hs software. The structure of the chapter is summarized as follows: 
\begin{itemize}
	\item Section \ref{designPatterns:state} is a review detailing the need for such a design process
	\item Section \ref{designPatterns:directTranslation} details a direct translation of models from literature to serve as a baseline and identify key issues (model reuse, scalability, replicability) that should be addressed 
	\item Section \ref{designPatterns:library} is an introduction of three Haskell modules and one testing framework which encapsulate the design patterns that address those key issues 
	\item Section \ref{designPatterns:discussion} discusses project structure using the patterns defined in Section \ref{designPatterns:library} and project maintenance techniques with version control
	\item Section \ref{designPatterns:Iterative} proposes a test-driven, iterative modelling process
\end{itemize}


\subsection{State-of-the-art}
\label{designPatterns:state}
Using game theory to inform cybersecurity problems has seen growth in recent years with the development of a number of different models for evaluating Denial-of-Service attacks on cloud infrastructures, intrusion detection systems, and advanced persistent threats. Refer to the following surveys \cite{Pawlick2019}, \cite{Hausken2024}, \cite{Manshaei2013} for an overview of the wide collection of game-theoretic models. 

A general procedure for developing these models can be (roughly) summarized in the following steps: 
\begin{enumerate}
	\item Detail the security scenario and system, vectors of attack, and defensive capabilities
	\item Develop abstractions  and parameters for the players, actions, and payoff in a game-theoretic setting according to the security scenario
	\item Solve for a solution concept (i.e. Nash equilibrium, Subgame perfect Nash Equilibrium) using methods such as linear programming or Q-learning (for stochastic or repeated games)
	\item Deploy new strategies or technologies in the system according to the solution concept above
	\item Conduct simulations with a fixed strategy, determine the highest expected utility for players and evaluate system performance under these conditions
\end{enumerate}

However, the most recent concerns with evolving attacker threats and dynamic security situations requires more complex game-theoretic models. These games can be part of a larger automated defensive system to update defensive strategies in real time as part of a larger infrastructure such as in \cite{Jin2018}, \cite{Zhu2012}. The progression of these models often relies on the extension and variation of these game-theoretic models. For example, we may need to consider scaling the number of players or repeating strategic interactions. The models presented in \cite{Chen2009}, \cite{Nochenson2012} suggest the use of the models as a basis for extensions and increased-complexity for other security scenarios. Similarly in \cite{Pawlick2015}, the signalling game structure are derived from \cite{Carroll2009}, with adjustments to the utilities. We'll see later how these models written in open games allow for easy extensionality.

According to \cite{Collins2025} evaluating 86 different game-theoretic models in cybersecurity, there already exists a sense of homogeneity between these models, where 76\% of models only cover a two-player security interaction, and 79\% use Nash (or variants of) equilibrium solution concepts for analysis. The authors also recommended a formal method for modellers to state their assumptions of the model that follow more in-line with cybersecurity concepts. Expanding on this idea in particular, we propose that code-based methods for stating assumptions allows for clear, testable specifications. Only 24 of the 86 studies shown consider "multiple variants" of the constructed model. The specification of two criterion: (1) "Efficacy of Modelling" and (2) "Practicality of Solutions" serve as a framework for evaluating the tractability of game-theoretic models' representation of the underlying real cyber-interaction. The resulting recommendations should then be considered: 
\begin{enumerate}
	\item The need for a game space abstraction 
	\item Allow for more flexible assumptions
\end{enumerate}

In that same vein, \cite{Egan2025}, \cite{Liang2013} call for better scalability of models, in particular addressing models that account for more than two player games. This falls more closely to tractable game models that more accurately reflect collaborative or networked defensive systems, but requires more complex equilibrium solutions. Similar to other game formulation methods, each model has a large input dataset of parameters to consider.

Is the open-games-hs software equipped to address some of these issues? This thesis draws on a key motivation proposed by Zahn in \cite{ZahnCybercat}, towards the synthesis of an encoded library of microeconomic models. The process of developing the "correct" model is therefore framed as a software engineering problem. The open-games-engine has demonstrated its use verifying the most recognizable game theory problems like Prisoner's Dilemma, to auction mechanisms. A series of these models have been met with production-level directions, and a codebase of models have grown. While this thesis departs from the application of this field towards cybersecurity, the bulk of the work that is presented here is an attempt to give guidelines for using the open-games-engine effectively. Specifically, the interdisciplinary and workflow possibilities that are provided by producing models in this environment, achieving easy maneuverability and testing that fits naturally with the requirements for synthesizing effective security models. 

\cite{20squares} has a series of completed projects for auctions and blockchain staking protocols. Capturing the complexity of models with open games is shown in these previous projects, but this chapter will deliberate on formalizing common techniques used to generate these models. We invite readers to refer to the README for \cite{20squares} projects for the syntax of the open-games DSL and common operators that can be used. 

Most recently, \cite{tan2022a} demonstrates the open-games-engine use-case for modular law and contracting clauses as a software library \textit{Clause2Game}. His thesis strongly ties software engineering methodologies to clause law methodologies, which is reminiscent of our approach. For example, the resultant data sets already begin to hint at the need for a methodology for "closing games" with equilibrium analysis driven by random initial conditions using \ensuremath{\Conid{\Conid{Test}.\Conid{QuickCheck}.Gen}}. We hope that by explicitly providing a metamodelling, iterative process, this would be applicable beyond the field of security and pertain to collaboration between domain experts and game theory / open-games modellers. But overall, the open-games-hs software can be adapted to fit the modelling needs of the target discipline.  

Extensions to the original thesis \cite{HedgesThesis} on compositional game theory has been explored over recent years specifically to accommodate a wider scope of solution concepts and games. Whether it's describing subgame perfect equilibrium in a market entry game (\cite{hedges2017morphismsopengames} or a methodology for translating games from extensive-form into open games (\cite{capucci2021translating}), there is still a major gap between these developments and \textit{open-games-hs}. While an exciting prospect (but out of the scope of this thesis), adding a pipeline for doing value-iteration to learn optimal policies for open games (\cite{hedgeslearning}) is possible. Further connections with control theory \cite{rodriguezsakamoto2026categorical} has continued to shed light on new avenues to take when doing game theoretic modelling with open games.

\subsection{Direct translation}
\label{designPatterns:directTranslation}
This study begins by following a procedure to first naively translate models from literature without any design patterns or meta-modelling structure. 

\begin{enumerate}
	\item Identify pre-existing security game models in literature 
	\item Implement these models to reproduce the expected results using open games
	\item Identify and generalize constructions used across models
	\item Analyze flexibility of models and analytical techniques 
\end{enumerate}

For the first step, we minimized our game type search to a particular subset of two-player cybersecurity games, in the broad setting with a defender in the role of deploying resources for protecting a computer network. An attacker also broadly falls to a role of attempting to access or control this computer network. We did not place restrictions on selecting these models to align by the technologies being assessed or a fixed type of cybersecurity attack, with the eventual aim to abstract these away from the game formulation. By reviewing the aforementioned surveys, we found that that many games falling under this classification can then be organized by a game-type (Bayesian, Stochastic etc.) each with their own notations, parameter restrictions, and payoff formulations. 

In the second step, the unstructured approach is used to establish a baseline for this study by hardcoding each of these specifications into a Haskell module. To maintain expressiveness and readability, we use appropriate variable names and global-scope constants for model-specific values. However, we wrote each of these modules in isolation, without considering any relationship or replicability in other modules. 

In the following chapter, we primarily focus on the third point by codifying specific design patterns for a more generalized game construction process. We chose four models from literature as detailed in Table \ref{table:baseline} to serve as the baseline for direct translation from the corresponding paper to its representation as open games. 

For the final step, no metric has been established for conducting a comparative analysis with other tools. We leave this for a future behavioural study, for security modellers across disciplines and skillsets to follow the presented design patterns to generate models. Possible metrics could involve productivity or real-system performance determined by the findings extracted from a model.

Lastly, the analysis in some of these models use solution concepts that have not yet been developed in open games like Bayesian perfect equilibrium and sequential equilibrium \cite{FUDENBERG1991236}. A decent chunk of investigative hours went into attempting to formalize these concepts in open games \footnote{see \textbf{SeparatingEquilbrium.hs} to see the class beer-quiche game.}, which resulted in a rabbit hole that was less pertinent to the overall target design process for modelling. Each step was dictated by a transition graph that described the status of the network following each action. In open games, solving for stationary equilibrium strategies would involve iterating over possible strategies (actions for each state), for each possible initial condition for the system, which quickly leads to a computationally unyieldy simulation.

\subsubsection{Module 3: designing payoffs}
We can also recognize the similarities between how these types are used for computing payoffs. The instantiation of games by action space informs the types exactly available for designing payoffs. Since a model doesn't 'require' any specific payoff behaviour beyond these types (and maybe fitting into a test infrastructure). We can loosely characterize payoff functions by their dependence on the following information: 
\begin{enumerate}
	\item The output of the open game 
	\item Model-level exogenous parameters from \textbf{Module 2}
\end{enumerate}

An example of 1. in a simple case is a tuple of actions chosen by each player in the game, or the assigned player type. 2. is concerned with system parameters that are relevant to payoff data. Here, we propose the reader monad as the necessary function-passing structure for generating payoff functions according to these model-level exogenous parameters. The reader monad is well-suited to passing a configuration in functional programs, and easily accessing fields of record type with the \ensuremath{\Varid{asks}} operator. Let's see how this is used in-production.

This supports the system-level-first architecture that allows a modeller to introduce relevant variables that are not directly involved and subject to manipulation separate from the interworkings of the open game model. Thus, we can actively test how different payoff schemes affect our game model, either by (1) testing the same game with different system variables or (2) the same system variables with different player capabilities. We can characterize a payoff profile's dependence on two things: the outputs of the open game, and the variables accessible with the \ensuremath{\Conid{PayoffReader}}.

Already we can consider branching the payoff functions into helpers associated with each type of player, and pattern-match on these types. \subsubsection{Module 4: property tests for model verification}
At this point, a modeller may be asking questions such as "is equilibrium reached under this system configuration and payoff calculations." After using the previous modules to construct a series of "executable" models, we need a concise way to organize our experiments. We use executable models to describe closed games (by type, ready to run diagnostics) but specifically instantiated with a payoff module and a parameter module call. This module leverages the Hspec testing library which has a nice tradeoff of writing human-readable specifications, and uses \textit{Gen} for these parameters to generate random test-data. 

A single experimentation test should be generalized under a broad goal using \ensuremath{\Varid{describe}}. The subsequent property tests are then defined using the \ensuremath{\Varid{it}} operators to designate the evaluation of a completed model. The \ensuremath{\Varid{property}} operator requires a boolean-valued function, so expectedly a modeller is in the position to extract properties based on this evaluation. \footnote{This resembles a model-checking approach in the multiagent-systems verification field, where a propositions are developed by a modeller which must be checked for each state of a state-transition structure}.

In terms of complexity, this evaluation is run for each test case of \ensuremath{\Varid{params}}. But how are these test cases generated? Precisely by the test data and model-wide data instantiation in \textbf{Module 1}. Without an explicit implementation of \ensuremath{\Conid{\Conid{Test}.\Conid{QuickCheck}.Gen}} for the supplied data type, we can end up with a number of test cases on the order of all the possible combinations over all the possible values within the natural range of each of the fields. This isn't computational feasible, but conceptually not useful to modellers anyways. Any experiment to extract results means investigating how one or two exogenous parameters affects equilibrium or payoffs. 

This module is intended to be a mixture of both a simulation script and a self-documenting specifications document. This is a vast improvement on a series of Haskell functions calling diagnostic functions on closed games. It's dynamic in the sense that tests can be added, removed, or refactored. The built-in test case generation can also provide modellers insight to how sensitive the model is to certain parameters. \footnote{For occasional graphical analysis, we used \ensuremath{\Conid{\Conid{Graphics}.\Conid{Rendering}.Chart}\mathbin{\circ}\Conid{\Conid{Backend}.Diagrams}} to plot payoffs for each player using the generated data.}  

\subsection{Discussion of design patterns}
\label{designPatterns:discussion}
Equipped with these modules to organize the development and analysis of a model, this should drastically improve the direct translation process from Section \ref{designPatterns:directTranslation}. But more than that, this provides some structure for the game formulation process which ultimately provides modellers with many advantages. 

Rapid generation of models is now possible, since many models can be off-shoots or variants for any given parameterization. The result could be multiple complete games that follow a singular high-level game formulation. The relationships between these variants can be explicitly controlled where it is commonly-used in literature, namely in payoff adaptation or stage game repetition. By fixing this process, practitioners have a common-platform to interpret these models. For example, practitioner Alice may be managing their own unique security situation, for which she can use \textbf{Module 2 and 3} to codify the model parameters. Alice's colleague Bob ran similar experiments but with an older configuration so the parameterization doesn't match, but the open games developed using \textbf{Module 1} by Bob are perfectly applicable. Then Alice's job could be as simple as importing Bob's library. Any future updates can then be maintained through standard Git source control and merging working branches. A future behavioural study involving practitioners of the relevant disciplines to be introduced to this workflow, then be tasked with a model to implement, in order to evaluate the efficacy of treating would help validate (or invalidate) the goals behind these design patterns.

These patterns overcome the rigidity of models by making them easily adaptable. Any changes are reflected across dependencies thanks to the Haskell typechecker, which helps maintain consistency across models and directs users to where changes need to be made. Then, any model adaptation or dependence on the security problem formulation is stratified more explicitly to modular adaptation in the Haskell environment. We can see this in Figure \ref{fig:HPadaptation} which stratifies model relationships along these patterns. In contrast with the direct translation process, the blue dotted line is is a concrete process, where "augment" makes minor adjustments corresponding to scaled payoffs according to new honeypot configs. The immediate question of how to consider this new factor in our game model can be written as an additional series of property tests within the same file, where a modeller can compare model performance.

\subsection{Iterative modelling using open games}
\label{designPatterns:Iterative}
% The spirit of this thesis has certainly been explored in other work, for example in the simulation procedure provided by \cite{Nochenson2012}. This thesis attempts to mechanize the claims for "easily extendable" or "replace lines 9-13 in Algorithm 1."
With the feedback loop established in \ref{fig:Workflow1}, we can begin to see a responsive, cyclical workflow. With standard software patterns in place, changing the implementation for these models to match changing specifications is a typical refactoring process. 

An iterative-style approach is alluded to \cite{wellman2006methods}, as a simulation-based approach to inform the general game-theoretic design process. According to section 6.1 on IDS optimization in \cite{Collins2025}, there is a recommendation for characterizing and distinguishing different kinds of attackers and varying objectives.  

Many game-theoretic models in security rely on ad-hoc schemes \cite{Liang2013}. The authors also cite a need for standards for designing payoffs and more scalable methods to match the complexity of the security problem, such as building a model that considers more than three players. The cybersecurity problem specifications dictate the parameters and format of the model, creating a hyper-focused game. So translating the real-world security situation to a model using the same toolbox of game-theoretic mechanisms implies the need for the right sandbox to test different real-world translations and how they respond in the game-theoretic model. 

The work conducted in \cite{Caulfield2015}, \cite{Caulfield2014} closely resembles compositional and software-supported approach in security modelling by \textit{a priori} designing models that can be composed together later. Here the authors present a systems modelling theory for security policy design. Using a semantic-approach based on process theories to model elements of a security situation as resources of these theories, these concepts can be encoded in Julia to run simulations. They show composition of models is well-defined and demonstrate how to run these models based on individual expected utility. The result is a model to help inform security policy managers make better decisions about security systems and have a framework to convey this information to other stakeholders.  

This modelling approach is focused on the security of an organization comprised of three sequentially-composable models: (1) a device-loss model, (2) a tailgating model, and (3) a document-sharing model. The pitch most strongly reminiscent to this thesis is that a modeller can adaptively see how including or excluding elements of a model to the workflow affects the system in a reactive way. For example, the modeller can examine the simulated data of just the tailgate model with and without the presence of a security guard on the frequency of computer accesses, and then observe the impact of the same presence of a security guard in the large composed model. This layered approach of designing locations and resources on a layer under the decision-making layer of agents hints at a design approach that separates the concerns of the model from its instantiation. This thesis tackles a different class of security problems but mirrors the task of formalizing security problems in a compositional and iterative way.

Furthermore, an iterative, formalized process for refining games is not new. In particular, \textit{empirical game-theoretic analysis} is a methodology that learns payoff profiles and strategy spaces through simulated data to inform the game formulation. Specifically, the goal is to instantiate an empirical game which is parameterized by simulating expected payoffs according to a strategy profile. Two feedback mechanisms are leveraged: (1) payoff estimation and (2) strategy space exploration.  This methodology has seen its applicability in moving target defense \cite{Wellman2015} and adaptive cyber defense \cite{Wellman2019}. Further extensions for a software-induced workflow, including database support and use of Gambit, can be found in \cite{EGTAOnline}.

\subsubsection{Towards test-driven open games}
Test-driven development (TDD) is a coding paradigm where a programmer begins with unit tests and iteratively refactors code to fulfill these tests and write new ones. A programmer doesn't move on to the next iteration until the entire test suite passes, ensuring that refactors don't cause breaking changes across a code-base. The very first test case in any situation is to verify the most basic assumptions for the behaviour of a program. And as the complexity and dependency of this program grows, these assumptions are always kept in check. TDD enables the coder to think about specifications first, and while those specifications are open to change over time, writing these tests document the expected behaviour of the program. 

By using TDD as a way to guide open games evaluations in a we can ensure guarantees and verify assumptions surrounding a game formulation before its eventual composition with others. Furthermore, the use of the previous design patterns means we don't have to treat an entire security model as a monolithic entity every time we fail a test. 

First, we make the following correspondence between types of tests in order to demonstrate different kinds of tests that can be written in our framework, summarized in Table \ref{table:TDD}. 


\begin{table}[h!]
\centering
\begin{tabularx}{\textwidth}{|l X|} 
 \hline
 Type of test & Description \\ [0.5ex] 
 \hline\hline
 Unit & Payoff module tests, parameter and data generation tests \\ 
 \hline

 \hline
\end{tabularx}
\caption{Summary of kinds of tests for TDD in open games}
\label{table:TDD}

Unit tests would ensure the correctness of the payoffs, test data, or helper functions that act as infrastructure to run the high-level specs that reflect the target security specification. We reserve Functional tests as the mechanism for verifying security needs through equilibrium checking. It follows that unit tests serve as a the test suite for the implementation of the model, so all unit tests should go green before running the functional tests. After both types of tests are passing, the results can be fed back to the top-level in order to inform the next iteration of models. Due to the compositional and interdependent nature of this methodology, the next iteration of models will have the previous iteration of models (and its components) at its disposal, like a typical software project. By following the TDD process as seen in Figure \ref{fig:TDD}, security models in open games can be iteratively improved upon, while maintaining consistency with the demands of stakeholders setting high-level specifications.
